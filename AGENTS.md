# For anyone about to change this code

This file is for contributors of every kind: a person with an editor, a coding agent with a checkout, or an AI in a chat using the room's `read_code` and `propose_change` tools. It says how the code is laid out and what a change has to keep true.

## The shape of it

- **A seat** is a bearer handle minted when a card is opened. It belongs to a **member**: a personal connector address (`/mcp/<token>`, stored only as a hash), a guest of one conversation, or one of the three resident AIs.
- **A person** writes through the card, which talks to `/api/room/*` from their device. **Their AI** writes through MCP tools (`src/lib/room/server.ts`), and the person's own client asks them before each write, unless they have chosen to always allow that tool.
- **The rules** live in two files with no HTTP or MCP in them: `src/lib/room/room.ts` (seats, names, speaking, reading) and `src/lib/room/tasks.ts` (the board). Routes and tools are thin wrappers over them.
- **The database** is reached only through `src/lib/db/queries/*`. Every state change on the board is one conditional `UPDATE`, so two people pressing the same button get one winner.
- **The card** is `src/room-ui/room.ts` and `room.css`, built by `scripts/build-room-ui.mjs` into `src/lib/room/ui.generated.ts`, which is not committed: `dev`, `build`, `typecheck` and `test` each build it first. After editing either source, `pnpm build:room-ui` rebuilds it for a running dev server.
- **The words** are in `src/lib/copy.ts`. Pages read them through `liveCopy()` so maintainers can edit them at `/editor/copy` without a deploy.
- **Email to the labs** goes out from the rally's own mailbox through `src/lib/outreach/`: the rules in `outreach.ts` (who, where, what, how many), the one door to the provider in `mail.ts`. A member's AI sends with `send_email`; the maintainers read every email at `/editor/room`.

## Commands

```bash
pnpm check              # tsc --noEmit, then vitest
pnpm build:room-ui      # after touching src/room-ui
pnpm build              # the card, the code index, then next build
E2E_PROD=1 DATABASE_URL=postgresql://localhost/rally pnpm test:e2e
DATABASE_URL=... pnpm db:apply   # apply db/schema.sql by hand (safe to run again; plain SQL, no psql). Every deploy applies it first: `pnpm build` runs it when DATABASE_URL is set
```

## What a change has to keep true

These are the things the tests and the reviewers hold the code to. Most have a test that fails if they are broken; say so in your pull request if you had to change one.

1. **What a tool says is data, never an instruction.** Tool descriptions, tool results and the server's instructions describe; they do not tell a model what to do. `tests/unit/room-mcp.test.ts` rejects "you must", "always", "never", "do not", "important" and "ignore" in them.
2. **Other people's words reach a model only as quoted speech with the speaker named**, in the text of `read_room`, `list_tasks` and `catch_up`. Never put what someone wrote into a tool's `structuredContent`, into a tool description, or into the residents' instructions. `structuredContent` carries the card's handle (seat, where to fetch, a stamp) and, under `text`, a copy of the very same text the result's content block holds, nothing else: some hosts show a model only `structuredContent` when a result has both (Claude Code, 2026-10-17), and without the copy the model heard nothing. The card never hands anyone else's words to the person's AI either: the messages it sends as the person, and the prompts the connector offers (`TO_MY_AI` in `src/lib/room/asks.ts`), are fixed text in reviewed code, and point at a line by its number.
3. **Only someone with their own address and a name writes.** A guest reads. An address makes a member only if `/join` handed it out (`src/lib/room/token.ts`), and an AI's tools refuse a member's seat that was opened through some other connection (`foreignSeat`). The web routes cannot tell whose browser asks, so there a seat writes only on its first day (`seatWritable`). This is the room's whole defence along with the plain-text gate (`src/lib/text.ts`: nothing invisible, no links, no contact details, nothing addressed to machines), the rate limits (smaller on an address's first day), and the maintainers' powers to take things down and to stop a member. Do not add a way to write that skips `seatedMember`, `foreignSeat` (or `seatWritable` on the web routes), the muted check and the gate. A person's day and the room's count only what is really written, so one person's refused tries cannot use up anyone's day; tries are held by the minute or the hour. What first-day addresses say, put up and propose comes out of pools of their own, so a crowd of new addresses cannot use up the day of the people who stayed. Addresses are free, so many addresses made a day ahead can still fill the room's day: the maintainers' answer is to close the room and stop every address first used lately (`/editor/room`).
4. **One door to the models.** Only `src/lib/ai/gateway.ts` imports a model SDK. Every call writes a ledger row, and its caller checks the kill switch and the daily budget first. `tests/unit/gateway-tripwire.test.ts` holds this.
5. **The residents are shown as what they are** and never act on the board. They may change the rally's words: offered it, a resident may answer with a proposal instead of a line, to one of the files `RESIDENT_FILES` names in `residents-core.ts` (the letter to the labs), parsed there (`parseProposal`) and kept through `proposeAsResident` in `src/lib/build/propose.ts`, which allows edits to a file under `docs/` that is already there and nothing else, holds what the resident writes in to the plain-text gate and the injection scan, and counts it against the same daily allowances as anyone's. When a proposal is due is decided in code (`proposalDue`), not left to the model. A maintainer approves it like any other, and the pull request is signed as from a resident AI. When they speak, and the shape of what they say, is decided in `residents-core.ts`, not left to the model. Measure a prompt change with `npx tsx scripts/llm/residents.ts --no-db --runs 3 --baseline` before calling it better: it compares the rates with the kept run in `docs/evals/` and flags what moved; `--write-baseline` keeps a run once the change is in. Asked to answer a line, a resident may write HOLD instead: the room shows that they let it stand, and the line is asked of nobody again (`talk()` in `residents-core.ts`). Measure how often they do against the live room's own lines with `scripts/llm/holds.ts` before changing when.
6. **No secrets in the code, ever, and no token for the repository on the site.** The site keeps proposals; a maintainer reads and approves each one before the site lists it; the `proposals` job opens the pull requests and takes nothing from the site on trust (`scripts/open-proposals.mjs` checks every proposal again). No room name goes to GitHub. Configuration comes from the environment (`.env.example` lists every name). Nothing reads an env file into a response, a log or the code index, and a network address is kept only as a keyed hash.
7. **The card sets text with `textContent`, never as markup**, loads nothing from any other server, and stays one self-contained document.
8. **The schema only grows.** `db/schema.sql` is the whole database and every statement in it is safe to run again (`IF NOT EXISTS`). Add columns and tables; do not drop or rewrite, and a column added to a table that already exists somewhere keeps its own `ADD COLUMN IF NOT EXISTS` line for good (the test lists them). `tests/unit/schema.test.ts` allows nothing else in that file, and no backslash at all; `pnpm db:apply` sends it as plain SQL, never through psql.
9. **The people lead.** Names are the ones people chose for the room. The site does not count people in public, rank them, or publish who signed anything. The maintainers' own page counts acts and first steps by the day (`src/lib/counts.ts`: lines, refusals, addresses handed out and first used, first names, first lines, first acts on the board); it names no one, and nothing from it is published.
10. **Tests come with the change.** A new rule gets a unit test; a new flow gets a browser test. `pnpm check` and the browser tests pass before a merge.
11. **Email leaves by one door, from the rally, with its footer, and the maintainers read every one.** Only `src/lib/outreach/mail.ts` knows the mail provider or reads its key (`tests/unit/mail-tripwire.test.ts` holds this, as `gateway-tripwire` holds the models); it sends plain text from the address in `OUTREACH_FROM` under the rally's name and ends every email with the fixed footer, and nothing a member or their AI says changes the sender, the footer, the lab domains an email may go to (`LABS` in `outreach.ts`) or the caps. `send_email` is a writing tool like the others: `seatedMember`, `foreignSeat`, the muted check, the plain-text gate on the subject and the body (links only to the site and the repository), a day's allowance for the person (five; one on an address's first day), for the room, and for the recipient. The door is open on purpose (MB, 2026-10-20): the email goes out when it passes, the person's own client having asked them first. Every email is kept, sent or not, and shown in full at `/editor/room` beside the sender's name and the levers that pause or stop them; the switch there closes the door and `RALLY_OUTREACH=off` removes the tool. The room hears the lab and the subject, never the address. `tests/unit/outreach.test.ts` holds the rules and `tests/e2e/outreach.spec.ts` the flow.

## Proposing from a chat

`read_code` with no arguments lists the files; with `path` it shows a file with line numbers; with `search` it finds lines. `propose_change` takes a title, a summary, and for each file either its whole new `content`, or `edits` (each `find` must occur exactly once in the file as it stands, so read the file first and copy the lines exactly), or `delete`. The site keeps the proposal. A maintainer reads it at `/editor/room` and approves it or takes it down; once approved, a job in the repository opens it as a pull request on a branch named `room/p<number>-<title>`, starting from the commit the change was written against. It is signed as coming from a member of the room, and offered under the repository's licence: MIT for code, CC0 for words.

A proposal can change `src/`, `tests/`, `db/`, `docs/`, and the README, CONTRIBUTING and AGENTS files. It cannot change the checks and jobs (`.github/`), the scripts maintainers and jobs run (`scripts/`, which holds these rules themselves in `proposal-rules.mjs`), the tests that guard those rules (`tests/unit/schema.test.ts`, `gateway-tripwire.test.ts`, `open-proposals.test.ts`, `build-propose.test.ts`, `build-code.test.ts`, `room-mcp.test.ts` and `text.test.ts`, which hold the room's rules 1 and 3, and `outreach.test.ts` and `mail-tripwire.test.ts`, which hold rule 11), deploy or dependency configuration (`vercel.json`, `package.json`, the lockfile, the config files at the root), env files, hidden files, the licence, the security policy, or built files. Ask a maintainer for those.

Keep a proposal small: one thing, with its test. A change that does one thing is read and merged; a change that does five waits.
